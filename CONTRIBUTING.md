# Contributing to GymTracker

Thanks for your interest in GymTracker! This guide explains how to run the project locally, how the code is organised and what we expect from a change before it is merged.

## Getting started

GymTracker is an [Expo](https://expo.dev) / React Native app written in TypeScript. It contains a local native module, so it **cannot run in Expo Go**: you need a development build on an emulator or a physical Android device.

Requirements:

- Node.js and npm
- Android Studio (SDK, emulator) or an Android device with USB debugging enabled
- JDK 17

```bash
npm install --legacy-peer-deps
npm run android        # builds the native app and installs it on a connected device or emulator
npm start              # starts the Metro bundler (use it once the development build is installed)
```

The native `android/` folder is generated by `expo prebuild` and is not committed. Never edit it by hand: change `app.json`, `app.config.js` or a config plugin in `plugins/` instead.

To add a dependency, use `npx expo install <package>` so that Expo picks a version that matches the installed SDK.

## Useful commands

| Command               | What it does                                               |
| --------------------- | ---------------------------------------------------------- |
| `npm run typecheck`   | Type-checks the whole project with `tsc`                   |
| `npm run lint`        | Runs ESLint through Expo                                   |
| `npm test`            | Runs the Jest test suite                                   |
| `npm run format`      | Formats the code with Prettier                             |
| `npm run db:generate` | Generates SQL migrations after you edit `src/db/schema.ts` |

## Project layout

```
src/app/        screens (Expo Router: every file is a route)
src/features/   screen-specific components (workout, exercises, history, charts)
src/ui/         design system: tokens, theme, primitives
src/db/         Drizzle schema, migrations, repositories, seed data
src/domain/     pure logic: units, 1RM, records, volume, plates, import and export formats
src/store/      Zustand stores: settings, active workout, rest timer, stopwatch
src/i18n/       translations (en.ts and ru.ts)
modules/        local native modules (rest-alert)
plugins/        Expo config plugins
drizzle/        generated SQL migrations
assets/         icons and splash screen
```

Keep non-route code (components, hooks, utilities) outside `src/app/`.

## Code style

The code should read like plain English, because it is read and edited by hand.

- Use full words for names: `exercise`, not `ex`; `index`, not `i`; `previous`, not `prev`.
- Name functions after what they do (`addSetToExercise`) and booleans as yes/no questions (`isCompleted`, `hasNote`).
- Keep files small. Once a file grows past roughly 250 lines, split it into named components under `src/features/<area>/`.
- Avoid clever one-liners. No nested ternaries deeper than one level: use early returns, a lookup object or a small helper.
- Put styles in `StyleSheet.create` at the bottom of the file, with descriptive keys (`exerciseNameColumn`, not `col1`).
- Comment why, not what. Obvious code needs no comment.
- Every user-facing string goes into both `src/i18n/en.ts` and `src/i18n/ru.ts`.

## Before you open a pull request

Run all four checks and make sure they pass:

```bash
npm run format
npm run typecheck
npm run lint
npm test
```

Add or update tests for any logic you change in `src/domain/` or `src/db/`.

## Commits and branches

- Write commit messages and branch names in English.
- Start the commit message with a short imperative line, for example `Add stopwatch to the clock sheet`.
- Name branches by purpose, for example `feature/year-calendar` or `fix/rest-timer-sound`.
- Keep a pull request focused on one change.
